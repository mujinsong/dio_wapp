# 账目核对与兑换恢复

## 兑换请求恢复

- 入口：用户“我的兑换”底部的“待核对的兑换请求”；兑换重试遇到响应归档时也会自动进入核对流程。
- `GET /api/v1/exchange/requests/:request_id?goods_id=...` 只查询当前登录用户的兑换请求，校验商品与原请求一致。
- 原订单关联在兑换事务中保存，归档详细响应后仍保留。旧版本尚未归档的响应，在维护任务归档前补存关联。
- 历史上已经归档且没有订单关联的请求，不猜测订单，提示用户先查看兑换记录。
- 用户可以查看原订单，或者选择“已核对”并再次确认解除本地旧请求。解除不会扣分或下单；下一次兑换仍需重新确认。
- 无记录、查询失败、登录账号变化或页面退出时，不清除旧请求。旧请求号在服务端始终保留，不会因客户端解除而重新执行。
- 兑换记录页切换账号后立即重置旧订单、核对按钮和分页状态；旧账号的迟到响应不会更新新账号页面。本地请求保存失败时不发起核对，保留原请求供重试。
- 数据库迁移 6 `exchange_recovery_reference` 增加关联字段，服务下次启动时执行。前后端需同步更新。本次开发未启动服务或迁移现有业务库。

## 管理员账目核对

入口：“经营概览”底部“账目核对”，仅事务所管理员可访问。

`GET /api/v1/admin/reports/reconciliation?agency_id=1&kind=accounts&cursor=0&limit=20`

`kind` 可选 `accounts`、`orders`、`stock`；游标按实体主键递增，单页最多 50 项，返回 `checked`、`issues`、`next_cursor`、`has_more` 和批次时间。接口与业务导出共享每用户每分钟 10 次限流。

核对范围：

- 积分：现有用户的事务所账户与显示余额、每条流水算术、首条流水期初值加累计变化、最后余额、相邻流水连续性。存在流水但账户缺失会报异常。
- 订单：每笔订单应有且仅有一条正确扣分流水；已取消或过期订单必须有匹配退款流水及退款关联；未退款订单不应有退款。同步检查扣库存、返库存的数量、状态和归属。
- 库存：现有商品（含软删除商品）的库存与流水算术、累计变化、最后数量和相邻流水连续性。
- 非零余额或库存没有流水时标为“待核对”，不直接判断为损坏；已有历史流水按首条期初值核对，不强行假定历史从零开始。

执行边界：

- MySQL 8.0+，每一批使用只读、可重复读事务；查询设 8 秒超时。不会自动修账、补流水、退款或处理过期订单。
- 页面每次最多请求三批，未完成时可继续；中断后从最后成功批次继续。可显示前 200 个问题，总问题数仍完整累计。
- 返回经营概览或下拉刷新时重新检查管理员权限，并清空旧报表和核对进度。普通网络中断可继续核对；权限失效时清空敏感数据，阻止其他在途请求重新填回旧报表。
- 日期筛选不影响账目核对，核对的是当前余额及全部历史流水。各批次不是同一个全局快照；营业中新增的记录或已扫描对象的变化，需要重新核对。
- 这是业务一致性检查，不代替财务审计。实体已被硬删除后遗留的孤立流水、线下真实收款、历史期初值的真实性，以及人为同时篡改所有相关记录，不在本轮覆盖范围。

## 真实 MySQL 并发回归

测试不启动 API。测试连接账号需要创建和删除测试库权限；每个测试使用随机 `dio_it_...` 库，结束后清理。连接串中原有业务库名会被忽略，绝不在原业务库建表。

在 `server/` 执行，连接串通过环境变量提供，勿提交凭据：

```bash
TEST_MYSQL_DSN='测试账号:密码@tcp(127.0.0.1:3306)/?parseTime=true' \
  go test -race ./internal/service -run TestMySQL -count=3 -timeout=3m
```

本机也可显式使用 `server/.env` 的本地 MySQL 连接配置（仅接受 localhost 或 127.0.0.1:3306）：

```bash
DIO_TEST_MYSQL_LOCAL=1 go test -race ./internal/service -run TestMySQL -count=3 -timeout=3m
```

覆盖八人抢最后一件商品、同一兑换请求八次并发、取消与核销竞争、双负责人同时审批，并验证 MySQL 上的只读对账。未设置测试环境变量时，默认跳过真实 MySQL 测试；CI 单独启动 MySQL 8.4 并强制执行三轮。

若进程被强行终止，清理函数可能没有执行。残留测试库需由运维核对名称和用途后删除，不要使用宽泛通配删除。
