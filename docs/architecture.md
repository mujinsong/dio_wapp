# 架构说明

项目采用单仓库管理，但运行架构是前后端分离。

```text
miniprogram
  -> HTTPS JSON API
  -> server (Go + CloudWeGo Hertz)
  -> Redis（兑换并发削峰，可降级）
  -> MySQL（积分、库存和订单最终一致性）
```

每个 API 实例的 MySQL 连接池最多打开 30 个连接、保留 10 个空闲连接；空闲连接 5 分钟回收，单连接最多使用 30 分钟，防止突发请求导致数据库连接数无界增长。

数据库变更由版本化迁移运行器管理，已执行版本记录在 `schema_migrations`。生产 MySQL 迁移使用命名 advisory lock 串行化多实例启动；迁移失败时不记录版本，修复后可安全重试幂等结构变更。

核心业务是事务所多团体模型：

```text
agency
  -> idol_group
      -> staff_members
      -> goods
      -> exchange_orders
      -> staff operations
```

工作人员权限按团体隔离，团体 A 的工作人员不能直接操作团体 B。

工作人员商品管理采用申请审批模式：查询直接读取所属团体的正式商品；新增、修改和删除写入 `goods_change_requests`，不会直接改变 `goods`。团队负责人提交本团队变更时会在同一事务内自动批准并写入正式商品，同时保留审计记录；负责人可以审批本团队其他工作人员的申请，管理员仍可审批事务所内全部申请。批准时后端再次校验提交人的团体权限；修改和删除还会校验提交时的商品快照，防止审批覆盖期间发生的库存或商品变更。一个商品同一时间只允许存在一条待审批的修改或删除申请。

团体不是商品标签。`idol_groups` 保存团体名称、说明、状态和排序，`goods.group_id`、`staff_members.group_id`、`point_ledgers.group_id` 与 `exchange_orders.group_id` 都引用真实团体。停用团体后，该团体商品不再出现在商店，工作人员权限和商品兑换也会失效，但历史记录仍会保留。

商品兑换先获取 Redis 商品级短期锁，再进入 MySQL 事务。Redis 锁用于限制热点商品同时进入数据库的请求数量；MySQL 的行锁、余额检查、库存检查、限购检查和订单写入负责最终正确性。Redis 故障时后端自动回退到 MySQL 行锁，不把 Redis 库存当作真实库存。

待核销订单允许用户取消，并默认带有 24 小时核销期限。后台周期扫描与用户查询都会结算已到期订单；用户列表只扫描当前用户自己的到期订单，详情接口先校验订单所有权再执行结算。取消、自动到期与工作人员核销都先锁定同一订单行，因此并发时只能有一个状态变更成功。取消或到期事务内同步返还事务所积分、更新用户余额镜像、恢复商品库存、写入退款流水并关联到订单。核销接口还会在事务内校验截止时间，防止扫描间隔内核销过期订单。批量到期结算会隔离单条异常，继续处理后续订单并汇总返回错误。期限和扫描间隔由 `ORDER_REDEEM_TTL_HOURS`、`ORDER_EXPIRY_SCAN_SECONDS` 配置。

商品支持 `sale_starts_at` 定时上架。未来上架的商品不会出现在商店团体、商品列表和详情中，兑换事务也会再次校验上架时间。生效判断在读取和兑换时完成，不依赖单机定时任务；如果同时设置限购窗口，限购从实际上架时间开始计算。

用户积分流水、兑换订单、积分审批和冲正申请采用按主键倒序的游标分页，避免历史数据增长后一次性加载。积分审批及本人/团队冲正列表接受 `cursor`、`limit`，默认每页 20 条、最多 50 条，返回 `page.items`、`page.next_cursor`、`page.has_more`，同时保留 `requests` 作为当前页兼容字段。小程序上拉加载下一页，切换团队、筛选或刷新时使旧请求失效，失败重试保留当前游标。管理员积分纠错先校验事务所权限并锁定用户和积分账户，调整后余额必须位于 `0..1,000,000,000`，纠错原因和操作人写入积分流水。登录接口按 IP 限频，认证接口按用户限频；二维码生成限制为每用户每分钟 30 次，CSV 导出限制为每管理员每分钟 10 次。限流器条目数量有上限，避免恶意来源制造无界内存增长。

积分余额、商品价格、库存、限购值和订单积分成本同时受服务层校验与数据库 `CHECK` 约束保护，避免异常代码路径写入负数或超大值。积分账户是权威余额，每次积分变更都会用事务后的账户余额同步用户余额镜像，修复历史镜像偏差。积分流水、订单和商品目录使用复合索引支持游标查询与商店筛选。

库存数量的每次变化都会在同一事务内写入 `stock_movements`：商品初始库存、管理员调整、商品申请生效、兑换扣减、用户取消返库和订单超时返库都有明确类型、操作人、关联业务编号及变更前后数量。管理员直接修改商品时提交读取到的 `updated_at`，后端锁定商品后执行乐观版本校验，防止编辑期间的兑换库存被旧快照覆盖。管理员经营概览按最多 90 天聚合购券、净入账积分、冲正、兑换和退款数据，并展示工作人员汇总、低库存数量和最近库存流水。

管理员业务明细对 `point_grant_requests` 和 `exchange_orders` 提供事务所权限隔离、日期/状态/关键词筛选与主键游标分页。CSV 导出复用同一筛选口径，限制为 90 天和 5000 条；导出文本以 UTF-8 BOM 编码，并对以 `= + - @` 开头的单元格添加文本前缀，避免表格软件执行外部输入形成的公式。

工作人员积分发放先形成 `point_grant_requests` 审计记录。购券模式由后端按单张面额乘购买张数重新计算积分，并保存唯一销售单号、收款方式、金额、张数、用户和操作人。普通工作人员单次达到 `10,000` 积分时只创建待审批申请；团队负责人自己的发放直接生效，负责人或管理员可审批其他工作人员的申请。每名工作人员每天最多预占和发放 `200,000` 积分，驳回申请会释放对应额度。批准时再次校验提交人权限，并锁定用户和积分账户后写入正式流水。

已批准发放记录的纠错使用 `point_correction_requests`，不修改或删除原申请与原流水。只有原提交人可以申请全额冲正；团队负责人只能审批本团体其他工作人员的申请，管理员只能审批所属事务所申请，提交人不能自审。批准事务锁定冲正申请、原发放记录、用户和事务所积分账户，余额充足时写入 `grant_reversal` 负数流水并更新余额；余额不足则整笔回滚并保持待审批。待审批和已批准状态通过唯一冲突键阻止同一原记录重复冲正，驳回后释放冲突键并要求记录驳回原因。冲正不返还工作人员当日额度，避免通过反复发放和冲正绕过每日上限。

工作人员工作台按工作人员、团体和自然日读取本人业务数据。额度读取与积分发放相同的 `staff_point_daily_usages` 口径并跨团体合计；收款汇总包含已批准和待审批售券，不包含已驳回记录；积分汇总以批准冲正后的净入账口径展示并单列冲正数量和积分；核销记录只统计 `redeemed_by` 为当前工作人员的订单。历史日期最多查询最近 180 天。

兑换、取消、核销、工作人员加积分、积分冲正、管理员积分纠错、工作人员商品申请和管理员新增商品都带客户端请求号。小程序在请求超时后会持久化并复用同一请求号，后端校验请求内容哈希并返回首次结果，避免“服务端已成功但响应丢失”导致重复扣款、重复加分、重复冲正或重复创建商品。管理员、负责人和工作人员关键权限在写事务内结合用户、事务所、团体及成员状态再次校验；商品和工作人员编辑还会校验读取时的更新时间，冲突后管理页面自动加载最新数据。审批驳回要求填写 2 至 512 个字符的原因。二维码令牌不写入本地持久存储；身份二维码页面会显示有效期，过期后停止展示可扫码图。

临时身份二维码由后台维护任务分批清理。幂等详细响应默认保留 7 天，到期后置空响应并标记 `compacted`，保留操作人、操作类型、请求号和摘要的唯一约束。重复请求即使在响应清理后也不会重新执行，而是返回 `operation_result_archived` 提醒核对业务历史；请求内容变化仍返回 `idempotency_conflict`。第 5 版迁移添加压缩标记和复合索引，清理任务只扫描未压缩记录。防重凭据长期保留，其数量随业务量增长；积分、订单、审批和库存审计记录不参与自动清理。升级前已删除的防重记录无法由迁移恢复。

小程序未确认操作不再按 15 分钟自动换号，持久化操作按账号隔离，并同时保存不同请求内容的未确认操作；确认成功后只清理对应请求号。退出或重新登录会使旧账户请求失效，并合并同时触发的登录请求。积分明细和兑换订单刷新、翻页及页面卸载使用请求版本检查，避免旧响应覆盖新结果或改写游标。

兑换接口 `POST /api/v1/exchange/orders` 要求提交 `goods_id`、`request_id` 和 `expected_price_points`。服务端在事务中锁定商品后核对确认价格，价格不符返回 `goods_price_changed` 并回滚，不扣积分、不减库存；缺少确认价格或超出范围返回 `invalid_expected_price`。小程序两个兑换入口均保留确认时的商品价格，收到价格变动错误后刷新商品并要求再次确认，不自动兑换。价格是首次执行的前置条件，防重标识仍基于原商品和请求号，已完成请求即使遇到后续调价也返回原订单，兼容升级前保留的未确认请求号。更新后端时需同步发布带确认价格的小程序版本，旧版本兑换请求将被拒绝。

所有请求在返回时检查统一的登录版本及凭据；退出或重新登录后，旧请求以 `session_changed` 结束，不进入成功回调。商店写回用户缓存和延迟跳转前再次检查登录状态。管理员积分纠错在确认时固定事务所、会员、积分变动和原因，查询期间禁止提交；确认时目标或账号已变化则取消操作，会员查询只接受最后一次结果。

HTTP 中间件为每次请求生成或校验 `X-Request-ID`，并在错误 JSON 中返回同一编号。访问日志使用路由模板而不是原始查询串，只记录方法、状态和耗时，避免 Token、二维码及搜索内容进入日志。所有 API 响应默认禁止缓存并启用 `nosniff`。

- 自动创建用户

- 普通用户、工作人员、管理员身份识别
- 事务所 / 团体作用域
- 开发环境 mock 登录
- 用户身份二维码
- 工作人员按团体加积分
- 线下购券销售单、每日额度和大额积分审批

- 工作人员当日额度、售券收款和本人核销工作台
- 商品兑换与库存扣减
- 兑换订单二维码
- 工作人员扫码核销兑换订单
- 待核销订单取消、积分退款与库存恢复
- 未核销订单到期自动退款与库存恢复

- 管理员按会员编号维护团队成员、负责人角色和启停状态
- 商店按团体筛选商品
- 用户分页查看积分流水
- 管理员按会员编号查询账户并执行受审计的积分纠错
- 管理员经营概览、工作人员业务汇总和低库存提示
- 管理员销售单与兑换订单筛选、分页和安全 CSV 导出
- 全链路库存变动流水
- 兑换订单游标分页
- 登录和认证接口限频
- 过期二维码定期清理与幂等响应压缩，长期保留防重凭据
- 容器化生产模板与数据库就绪检查

仍需部署环境提供 HTTPS 域名、微信后台合法域名、对象存储和订阅消息模板。积分来自线下购券，不开放用户自由转赠，避免积分倒卖和来源追踪失效。
