# dio_wapp

地偶/现场活动场景的微信小程序积分兑换项目。

项目用途、角色权限、业务流程和上线验收请先阅读 [项目说明.md](./项目说明.md)。

当前第一阶段已搭好：

- `server/`: Go + CloudWeGo Hertz 后端
- `miniprogram/`: 原生微信小程序
- `docs/`: 业务和接口设计
- `deploy/`: 本地依赖配置

当前业务结构是 `事务所 -> 团体 -> 商品/工作人员/业务记录`。团体是独立业务实体，不是商品标签；管理员可以维护团体、成员角色和商品，商品必须归属一个已启用团体。工作人员可以查询所属团体的商品并提交新增、修改、删除申请；团队负责人拥有工作人员的全部权限，可直接修改本团队商品，并审批本团队工作人员的申请。商品支持定时上架，开始时间前不会展示或允许兑换。

用户可以查看分页积分流水和兑换订单。管理员可以按会员编号核对账户并执行受审计的积分补加或扣减；每次纠错都记录操作人、原因和调整前后余额。待核销订单支持幂等取消，积分退款与库存恢复在同一事务完成。

“我的兑换”新增待核对请求入口。响应归档后可查询原订单；用户确认已经核对后，才会解除本地旧请求，且不会自动再次兑换。管理员“经营概览”新增只读账目核对，覆盖积分余额和流水连续性、订单扣分及退款、库存及返库记录。详细范围和真实 MySQL 测试方法见 [账目核对与恢复说明](./docs/reconciliation.md)。

线下购券积分由后端按面额和张数计算并生成销售单号。普通工作人员单次达到 1 万积分时进入团队负责人或管理员审批，每名工作人员每日最多提交和发放 20 万积分。兑换订单默认 24 小时内核销，超时后系统自动退积分并恢复库存。

管理员可以在“经营概览”按 1 至 90 天查看购券金额、净入账积分、已冲正积分、兑换、退款、待审批、低库存和工作人员汇总。所有库存变更都会在业务事务内写入库存流水，包括建档、人工调整、商品申请生效、兑换扣减、取消返库和超时返库。商品申请历史使用游标分页，管理员可按审批状态查看准确总数并继续加载。管理员保存商品时会校验编辑快照，期间发生兑换或其他修改就要求刷新，避免旧页面覆盖实时库存。

管理员还可以在“业务明细”按最近 90 天、状态和关键词查询销售单及兑换订单，使用游标继续加载，并将当前筛选结果导出为 UTF-8 CSV。单次导出最多 5000 条，文本字段会进行表格公式注入防护。

工作人员可以在“员工工作台”按团体和最近 180 天日期查看本人售券金额、支付方式汇总、净入账积分、已冲正积分、待审批积分、本人核销订单及当日剩余发放额度，并可直接进入加积分和核销操作。已驳回售券不会计入收款汇总，待审批售券会保留在当日对账数据中。

工作人员发现本人已入账积分有误时，可以从工作台对原记录发起全额冲正。团队负责人可审批本团体其他工作人员的申请，管理员可审批所属事务所申请，任何人都不能审批自己的申请。批准后系统保留原发放记录并新增负数冲正流水；会员余额不足时不会执行，驳回必须记录原因，同一原记录不能重复冲正。

涉及积分、积分冲正、库存和商品创建的写操作使用客户端请求号防重；网络超时后直接重试会复用原请求号，不会重复扣款、加分、冲正或创建商品。余额、价格、库存和限购值同时受服务层与数据库约束保护。管理员及负责人权限会在写事务内再次复核，审批驳回必须填写原因，避免请求检查后权限变化或无依据驳回。

后台维护任务会按批次清理过期身份二维码和超过保留期的幂等响应，默认每小时执行一次、详细响应保留 7 天。请求号、操作人和请求摘要长期保留为防重凭据，超过响应保留期的重复操作返回 `operation_result_archived`，不会重新执行；需核对业务历史记录。业务订单、积分流水、审批记录和库存流水不会自动删除。订单到期批处理会隔离单条异常并继续处理后续订单，同时返回聚合错误供日志和监控发现。可通过 `MAINTENANCE_SCAN_SECONDS`、`IDEMPOTENCY_RETENTION_HOURS` 调整响应保留期，防重凭据数量随业务量增长。

## 本地启动后端

1. 启动 MySQL：

```bash
brew services start mysql
```

同时启动 Redis（用于兑换请求削峰，Redis 不可用时会回退到 MySQL 行锁）：

```bash
brew services start redis
redis-cli ping
```

2. 启动 API：

```bash
cd server
go mod tidy
go run ./cmd/api
```

3. 配置真实微信登录：

```bash
# server/.env
WECHAT_APPID=你的微信小程序AppID
WECHAT_SECRET=你的微信小程序AppSecret
JWT_SECRET=至少32位的随机字符串
```

小程序 AppID 在这里配置：

```text
miniprogram/project.config.json
```

4. 测试 mock 微信登录（只用于本地）：

先在 `server/.env` 显式设置：

```text
APP_ENV=local
MOCK_LOGIN_ENABLED=true
```

```bash
curl -X POST http://127.0.0.1:8888/api/v1/auth/wechat-login \
  -H 'Content-Type: application/json' \
  -d '{"code":"mock:openid_001"}'
```

mock 登录必须同时满足 `APP_ENV=local` 和 `MOCK_LOGIN_ENABLED=true`。需要 mock 管理员时，还要把对应 OpenID 显式加入 `ADMIN_OPENIDS`；需要 mock 工作人员时，把对应 OpenID 加入 `STAFF_OPENIDS`；需要团队负责人时加入 `TEAM_LEADER_OPENIDS`。这些成员配置只用于首次绑定默认团体，之后由管理员人员管理页面维护角色和启停状态。

## 小程序联调

用微信开发者工具打开 `miniprogram/` 目录。

本地默认 API 地址是：

```text
http://127.0.0.1:8888/api/v1
```

当前小程序默认使用真实微信登录。如果需要临时使用 mock 登录，把下面文件里的 `useMockLogin` 改成 `true`，并按上面的说明开启后端 mock 登录：

```text
miniprogram/utils/config.js
```

## 登录失败排查

小程序点击“微信一键登录”后，需要先能访问后端：

```bash
curl http://127.0.0.1:8888/healthz
```

如果连不上，说明 Go API 没启动，登录一定会失败。

真实微信登录还需要在 `server/.env` 配置：

```bash
WECHAT_APPID=你的小程序AppID
WECHAT_SECRET=你的小程序AppSecret
```

如果只是本地先看页面和登录流程，可以同时开启小程序 `useMockLogin` 和后端 `MOCK_LOGIN_ENABLED`。生产环境会拒绝 mock 登录、默认 JWT 密钥、root 数据库账号以及缺失的微信密钥。

本地跑兑换核销闭环时可以准备两个 mock 账号：

```text
ADMIN_OPENIDS=mock_admin_openid
STAFF_OPENIDS=mock_staff_openid
TEAM_LEADER_OPENIDS=mock_leader_openid
```

普通用户兑换商品后进入“我的兑换”查看核销码；待核销订单可以由用户主动取消，取消事务会同时退回积分、恢复库存并记录退款流水。工作人员账号登录后进入“员工核销”扫码完成核销，已核销订单不能取消。

这是单事务所项目，数据库通过单例唯一约束禁止创建第二个事务所。积分在唯一事务所内通用，多个团体共用同一用户余额。

## 生产容器

生产容器模板位于：

```text
server/Dockerfile
deploy/docker-compose.prod.yml
deploy/.env.prod.example
```

部署前需要准备独立的生产密钥和数据库密码，并把 `.env.prod.example` 对应值写入部署环境。API 提供：

```text
GET /healthz
GET /readyz
```

服务会严格解析数字和布尔环境变量；变量格式错误或数值过大时直接拒绝启动并报告变量名，不会静默使用默认值。

首次生产部署必须在 `.env.prod` 的 `ADMIN_OPENIDS` 中至少填写一个管理员 OpenID，多个账号使用英文逗号分隔；`STAFF_OPENIDS` 和 `TEAM_LEADER_OPENIDS` 可用于首次绑定工作人员和团队负责人。配置仅创建缺失的成员关系，不会在后续登录时恢复已被管理员停用的成员。

`/healthz` 用于进程存活检查，`/readyz` 会检查 MySQL。生产环境还必须在容器前配置 HTTPS 反向代理，并由代理覆盖可信的 `X-Forwarded-For`；微信小程序后台需要配置同一 HTTPS API 域名。

后端数据库连接池默认最多打开 30 个连接、保留 10 个空闲连接，并定期轮换长连接，避免突发流量无限占用 MySQL 连接。多实例部署时需按“实例数 × 30”核对数据库连接上限。

登录、普通 API、二维码和导出接口使用分级限流。Redis 可用时限流计数由所有 API 实例共享；Redis 临时不可用时自动退回单实例内存限流，业务继续可用且仍保留基础保护。

数据库结构和一次性数据回填由 `schema_migrations` 记录版本。启动时只执行尚未应用的迁移；MySQL 使用 advisory lock 保证多实例只有一个进程执行升级，已应用版本的名称发生变化时会拒绝启动，避免历史迁移被静默改写。

生产数据库备份使用：

```bash
deploy/backup.sh
```

脚本默认读取 `deploy/.env.prod`，将一致性 SQL 快照、gzip 压缩包和 SHA-256 校验文件写入 `deploy/backups/`，目录和文件仅当前用户可读。备份文件不能只保存在部署服务器上，应同步到独立存储并定期在隔离数据库执行恢复演练。

可在生产 MySQL 容器中执行隔离恢复校验：

```bash
deploy/restore-check.sh deploy/backups/dio_wapp-时间.sql.gz
```

恢复校验会先验证 SHA-256 和 gzip 完整性，再导入随机命名的临时数据库并检查核心表、迁移历史和表结构，退出时自动删除临时数据库。脚本不会覆盖或写入 `dio_wapp` 正式数据库。

生产 API 容器以非 root 用户运行，文件系统只读、移除全部 Linux capabilities 并禁止进程提权；运行时仅提供受限的 `/tmp` 临时目录。

每个 API 请求都会返回 `X-Request-ID`，错误响应也包含 `error.request_id`。服务端访问日志只记录请求编号、方法、路由模板、状态码和耗时，不记录查询参数、请求体、Token 或二维码内容；小程序遇到服务端 500 错误时会显示该编号以便排查。

GitHub Actions 会在每次推送和拉取请求中执行后端测试、竞态检测、静态检查、构建、可达漏洞扫描，以及小程序和部署文件语法检查。工作流只授予仓库内容读取权限，不保存 checkout 凭据，也不包含发布步骤。
